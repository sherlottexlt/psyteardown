## 1. 问题与根因

不截断对照实验的**意外发现**:潮汐拆解中约五分之一的映射引用了输入里不存在的细节。
两次运行都如此,与检索层改动无关:

| | 基线 `max_n=8` | 实验 `max_n=12` |
|---|---|---|
| 触碰事实边界的映射 | 11 / 40(27.5%) | 9 / 42(21.4%) |

根因不在提示词措辞,在**结构**。`steps.py::map_features` 每次 LLM 调用只送进三样东西:

1. 框架简介 `_frameworks_brief`
2. 产品名
3. **一个功能名字符串**(`targets = [f.name for f in profile.features] + profile.touchpoints`)

产品原文**从未进入 step3**——包括 `chaoxi.txt` 里那整段「【事实边界】不得编造」,step3
一个字都没看到。连 step1 自己解析出的 `feature.description` / `user_goal` 也被丢弃。

模型在被要求描述它从未见过的界面。它不是在撒谎,是在填空。实验产物里的痕迹与这个
结构完全对应:

| evidence 原文 | 问题 |
|---|---|
| 计时器「**可能**配有环形进度条」 | 模型自己在对冲 |
| 睡眠模块展示「已连续打卡 X 天」,以**徽章**、进度条强化 | 事实边界明写不得假设徽章;且连续记录是独立功能,不属睡眠模块 |
| 课程显示「**还剩5:00**」 | 凭空发明的 UI 文案 |
| `feature` 字段写成「睡眠模块 - 连续睡眠打卡」 | 该功能名 step1 从未产出,是模型自拼的 |

## 2. 目标与非目标

**目标:** 报告中陈述产品事实的字段,只能是输入原文的逐字片段;做不到就不产出该条映射。

**非目标(本次明确不做):**

- step4 / step5 的溯源。二者的输入就是 step3 的输出,源头干净则下游断源;且它们是
  归纳性输出,强制逐字引用未必成立。
- LLM 裁判。已决定留作后续阶段(见 §9)。
- 检索层的任何改动。`retriever.py` / KB YAML 一律不动。

## 3. 方案:`evidence` 的语义收紧

`Mapping` 现有两个自由文本字段。编造全部发生在 `evidence`,因为它被要求陈述**事实**,
而模型没有事实来源。改动是把两个字段的分工划清:

| 字段 | 现在 | 改后 |
|---|---|---|
| `evidence` | 自由描述界面表现 | **原文中支持该判断的逐字连续片段** |
| `rationale` | 为何有效 | 不变,承担全部解释与推理 |

字段类型不变(`str`),存量案例照常 `Case.model_validate_json`,无需迁移。

### 为什么不是「新增 source_quote 锚点字段」

那样只能证明「存在一个真实锚点」,证明不了 `evidence` 那段话本身没编——模型完全可以
引用「支持定时关闭」这句真原文,再在 evidence 里继续写「可自定义 5/10/15 分钟三档」。
本次要修的正是后者。而 `evidence` 恰是 step4 的输入(`steps.py:104`)与报告里读者
看的那一行。

### 为什么不是「原文分句编号 + 返回句子 ID」

校验会退化成 ID 范围检查,**丢弃率趋近于 0**,而我们指望丢弃计数当可重复的编造率
度量。且 `list[int]` 会让存量案例反序列化失败。

## 4. 架构

新增纯函数模块 `src/psyteardown/pipeline/grounding.py`,不认识 LLM:

```python
MIN_QUOTE_CHARS = 6

def normalize(text: str) -> str: ...
def is_grounded(quote: str, source: str) -> bool: ...
```

独立成模块而非塞进 `steps.py` 的理由:这是全流程唯一**确定性可测**的部分,离线测试
能完整覆盖;混进 `steps.py` 就只能靠 FakeProvider 间接测。`steps.py` 现 133 行,不该再长。

数据流(三处透传,`description` 现在只到 step1 就断了,见 `orchestrator.py:30`):

```
run_teardown(description, ...)
  └─ steps.map_features(provider, profile, frameworks, description=description, ...)
       ├─ prompt 加入产品原文全文
       ├─ LLM 返回 MappingList
       └─ 逐条 grounding.is_grounded(m.evidence, description)
            通过 → 保留;不通过 → 丢弃并记账
```

`map_features` 返回值由 `list[Mapping]` 改为 `tuple[list[Mapping], GroundingStats]`。
调用方只有 `orchestrator.run_teardown`。

## 5. 归一化与校验规则

### 5.1 必须归一化 —— 实测依据

拿潮汐 step1 输出的 9 条功能描述(本就贴着原文写)比对原文:

| 匹配方式 | 命中 |
|---|---|
| 逐字原样 | **1 / 9** |
| 归一化后 | **6 / 9** |

**不做归一化会丢掉 89% 的真实引用。** 未命中的 3 条是模型加了「提供」这类前缀词
(真改写,非标点问题)。注意:这 9 条是在**没有**「逐字复制」指令下产出的,加指令后
合规率应显著高于 67%——但该风险是实打实的,故由 §8 标准 3 兜底。

### 5.2 规则

`normalize` 三步:

1. `unicodedata.normalize("NFKC", text)` —— 处理全角形式。实测 NFKC 覆盖
   `，；：（）！？０Ａ` 与全角空格,但**不覆盖** `。、「」《》·—`
2. `.casefold()` —— 英文大小写
3. 只保留 `str.isalnum()` 为真的字符 —— 一举去掉全部空白与标点,含 NFKC 漏掉的那些

`is_grounded(quote, source)` 为真当且仅当:

- `len(normalize(quote)) >= MIN_QUOTE_CHARS`(6),且
- `normalize(quote) in normalize(source)`

**为什么直接删标点而不逐个映射:** 更简单,且严格更宽松——标点差异永远不会造成误伤。
代价是理论上标点不同的两段文字会被判为同一段,实践中要撞上需要完全相同的字符序列。

**为什么设最短长度门槛:** 否则「专注」这类两字词天然是子串,能通过校验却什么都不证明。
6 是 `支持定时关闭` 这类最短有效引用的长度。它是可调常量,由单测锁定。

### 5.3 边界情况

- `m.error` 非空的条目(LLM 调用失败占位)**不参与校验**。它们 `evidence=""`,已被
  报告单独标为失败,不应再计入丢弃。
- `evidence` 为空字符串:归一化后长度 0 < 6,判为不通过 → 丢弃。

## 6. 计数与呈现

新增模型(`schemas.py`):

```python
class GroundingStats(BaseModel):
    kept: int = 0
    dropped: int = 0
    dropped_mappings: list[Mapping] = Field(default_factory=list)
```

三个字段只统计**参与校验的条目**,即 `m.error` 为空者。`kept + dropped` = LLM 成功
返回的映射总数,**不含**调用失败的占位条目。失败占位条目照旧进入 `TeardownResult.mappings`
并由报告单独标注,不出现在任一计数里。

`TeardownResult` 增加 `grounding: GroundingStats = Field(default_factory=GroundingStats)`。
带默认值,旧案例 JSON 照常反序列化。

**保留被丢弃条目的完整 `Mapping` 而非只存计数**,理由见 §8 标准 3:丢弃计数会混入
「模型改写了原文」这类误伤,必须能事后逐条归类为「真编造」还是「改写误伤」。复用
现有 `Mapping` 模型,不新增类型。

报告渲染(`render.py`)三处:

1. 逐条的「体现:」改为「**原文依据:**」
2. 拆解小节末尾,若 `dropped > 0`,加一行「本次丢弃 N 条未溯源映射(参与校验共 M 条)」,
   其中 N = `dropped`,M = `kept + dropped`
3. 新增附录「未溯源而丢弃的映射」,逐条列出 feature / framework / evidence,供人工归类

## 7. `feature` 字段漂移

step3 本就按 target 逐个调用,故在保留每条映射时直接覆写 `m.feature = target`。

这消除「睡眠模块 - 连续睡眠打卡」这类幽灵功能名。代价:模型偶尔会有意义地细分一个大
功能,覆写会把它压平成重复的功能名。判断是二者不对等——幽灵功能名是事实层面的错,
有意义的细分可以写进 `rationale`。

## 8. 验收标准(锁定于实现与实验之前,不得事后调整)

**对照基线:** 归档案例 `.field-test/experiments/chaoxi-maxn12.json` —— 42 条映射,
其中 9 条触碰事实边界(21.4%)。

**实验:** 同一输入 `.field-test/products/chaoxi.txt` **逐字不变**,provider 同为
DeepSeek,同样 `--max-n 12 --self-review`。唯一变量是本次改动。

| # | 标准 | 阈值 |
|---|------|------|
| 1 | 保留映射的人工事实边界越界率 | **≤ 5%** |
| 2 | 保留映射条数 | **≥ 25** |
| 3 | 丢弃样本人工归类中「真编造」占比 | **≥ 50%** |

**标准 1 的判定方法(定死,避免事后松口径):** 逐条读保留映射的 `evidence` 与
`rationale`,对照 `chaoxi.txt` 第 14~21 行那 7 条【事实边界】。只要出现该清单禁止的
内容(具体数值、强制路径/自由跳选、社交或协作功能、徽章等级排行榜、免打扰、连续天数
补签冻结、原文未写出的界面文案或动画细节),即计为一条越界。与基线 9/42 用的是同一
把尺子。

**标准 3 中「真编造」的定义:** 被丢弃条目的 `evidence` 描述了原文中**不存在的事物**
(如徽章、"还剩5:00")。反面是「改写误伤」——所述内容原文确实有,只是模型换了词或加了
前缀(如原文「雨声、海浪…」被写成「提供雨声、海浪…」)。归类以后者为准时算护栏误伤。

标准 2 防的是退化解:**全丢光不算赢**。基线 42 条,若保留数掉到个位数,说明护栏把
拆解本身也毁了。

标准 3 防的是**指标污染**:若多数丢弃其实是「模型改写了原文」而非编造(见 §5.1 那
3 条加前缀的),说明逐字要求过严、在误伤,应调 prompt 或引入覆盖率匹配,**而不是收工**。
这条不通过时不得宣称成功。

### 明确不作为依据

- **自评总分**。v7 spec §9 已记该指标不可用于比较版本优劣;不截断实验 §4 重申。
- 报告总字数、映射总数、丢弃总数本身。
- 我读完报告后的主观印象。前两轮已各犯过一次自证式验证。

## 9. 已知局限(实现前就写下,不得事后当成发现)

1. **本方案不能保证 `rationale` 里不夹带编造事实。** 它保证的是:描述产品事实的字段
   只剩逐字引用一条,编造被挤进一个明确标着「这是推理」的字段。这是把问题**收敛并
   标记**,不是消灭。
2. **子串校验只能证明「引用存在」,证不了「引用支持该结论」。** 模型可以引用一句真
   原文去支撑一个不相干的框架判断。要管这一层必须上 LLM 裁判,已决定留作后续阶段。
3. 归一化删除全部标点,理论上会让标点不同、字符序列相同的两段文字互相命中。
4. 报告可读性下降:「原文依据」是一句干涩的原文,不再是润色过的描述。

## 10. 后续方向

- **LLM 裁判**(已与用户确认作为下一阶段):拿原文 + 每条 evidence/rationale,判
  「该引用是否支持该结论」。补的正是 §9 第 2 条。
- 若标准 3 不达标,先做覆盖率匹配(最长公共子串 ≥ 引用长度的某比例)再谈其他。
- 不截断默认值改动(`2026-08-05` spec §8 第 1 条)仍开放,与本次独立。
