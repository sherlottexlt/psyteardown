# psyteardown AI Product Studio 北极星与产品形态规格

- 日期：2026-09-20
- 状态：方向基线，供后续产品设计、领域建模和实施决策使用
- 层级：平台上位产品规格
- 既有研发内核：仓库当前的 Discovery、Experience、Design、Engineering 与 Quality 代码及测试；旧开发文档仅在本地保留
- 目的：记录 2026-09-20 关于平台真正要做什么、用户如何使用、AI 如何完成大部分工作以及技术栈如何演进的讨论结论

## 0. 决策摘要

psyteardown 的长期目标不应局限于特定场景的产品拆解、体验评审或工程协同，而应成为一个面向个人与企业的 **AI Product Studio（AI 产品生成与演化平台）**。

平台接受的输入不是一份已经完整的产品设计，而可以只是一个不完整的愿望、现实困扰、商业目标、现有产品问题或正在推进的项目。平台负责把它逐步发展成：

1. 对目标、用户、情境、约束和成功标准的可纠正理解；
2. 多个具有真实差异的产品论点和实现路径；
3. 可运行、可体验、可测量的产品；
4. 与关键声明绑定的证据、未知、风险和适用边界；
5. 可以部署、制造、执行或继续演化的交付物。

北极星表述：

> 用户带来的不必是完整产品设计，而是一个值得改变的现实；平台负责把它发展成经得起使用、验证和持续演化的真实产品。

平台的主要用户界面应是一个 **对话驱动、成果物中心、长期运行的产品工作空间**。聊天是表达意图、纠正理解和发出指令的入口，但不能成为唯一界面。CLI 与 MCP 继续存在，但分别作为自动化/运维入口和外部 AI/IDE 接入通道，不再承担普通用户的主要产品体验。

首选技术路线：

```text
React + TypeScript + Vite Product Studio
                  ↓
          FastAPI Application API
                  ↓
现有 Python/Pydantic 领域内核 + 新增产品意图与结果层
                  ↓
持久化工作流 / 工具适配 / 隔离执行 / 真实验证
                  ↓
本地 SQLite + 内容寻址资产存储
后续 PostgreSQL + S3-compatible storage + durable workflow runtime
```

当前代码中的证据模型、体验假设、设计候选、revision/dependency graph、stale/invalidation 传播和工程 Gate 不应推倒重写。它们应成为新平台的可信研发内核。

## 1. 为什么需要重新定位

### 1.1 当前系统已经解决的问题

现有平台在以下方面已经形成了有价值的基础：

- 把观察、解释、预测和验证分开；
- 把心理机制作为条件性假设，而不是普遍真理；
- 保存候选、评审、实验和工程对象的 revision 与 provenance；
- 让上游变化传播为下游 stale/invalidated；
- 区分设计派生资产、仿真结果、样机测量和正式证据；
- 让 AI 提议和解释，但不伪造现实验证或自动批准高风险 Gate；
- 支持产品拆解、体验假设、设计反馈、工程对象和质量验证之间的连接。

这些能力回答的是：

> 当一个项目的场景、目标和候选方向已经相对明确时，怎样更可信地研究、设计、工程化和验证它？

### 1.2 当前系统没有解决的问题

现有流程默认用户已经能够提供相对明确的 `goal`、`target_segment`、`context` 和 `DesignBrief`。现实中，个人和企业用户通常只有：

- 一个模糊愿望；
- 一个反复出现但尚未解释清楚的困扰；
- 一个商业结果目标；
- 对现有方案的不满；
- 一些相互冲突的利益和限制；
- 一个做到一半、不知道下一步怎么推进的项目。

如果平台要求用户先成为产品经理、研究员和系统设计师，才能正确使用平台，那么平台只是把困难转回给了用户。

因此，需要在现有 `Discovery → Experience → Design → Engineering → Quality` 之前增加更上游的能力：

```text
不完整意图
  → 意图协商
  → 问题与现实建模
  → 结果契约
  → 产品论点搜索
  → 实现与验证
```

### 1.3 本次调整不是扩大品类列表

新方向不是把“App/穿戴设备”扩展成更多品类，也不是增加更多 Agent。真正的改变是平台的工作单位：

- 旧默认单位：一个待拆解或待评审的产品；
- 新默认单位：一个用户希望在现实中改变的结果，以及为了实现该结果而不断演化的产品系统。

软件、硬件、服务、内容、工作流和组织流程都只是可能的实现形式。

## 2. 平台是什么

### 2.1 产品定义

本平台中的“产品”定义为：

> 一套能够在特定条件下，持续为特定人群改变某个目标结果，并且可以被交付、运行、验证和维护的系统。

这一定义意味着：

- 一个漂亮原型不一定是产品；
- 一份完整报告不一定是产品；
- 一段能运行的代码不一定产生用户需要的结果；
- 一个硬件结构可制造，也不等于用户愿意并能够正确使用；
- 有时正确答案不是创建新产品，而是调整现有工具、服务或流程。

平台应忠于用户希望改变的结果，而不是忠于“必须生成某一种东西”。

### 2.2 平台核心承诺

平台的核心承诺不是“一句话生成 App”，而是：

> 在用户无法预先写出完整产品设计的情况下，替用户承担大部分研究、方案搜索、设计、实现、测试和修复工作，并在需要价值判断、现实资源或不可逆授权时，让用户以最低必要认知负担参与。

### 2.3 平台不是什么

- 不是只输出心理学分析的工具；
- 不是给产品打“心理学总分”的裁判；
- 不是只生成界面和代码的 App Builder；
- 不是用聊天记录代替项目状态的通用聊天机器人；
- 不是把任务分给大量 Agent 就算完成工作的编排演示；
- 不是只记录流程、但不负责交付结果的项目管理系统；
- 不是用仿真、渲染或 AI 自评代替真实使用结果；
- 不是承诺从通用规律计算出唯一“最佳产品”的自动设计机。

## 3. 服务对象与共同内核

### 3.1 个人用户

个人用户可能带来：

- 一个生活或工作问题；
- 一个创意；
- 一个想出售或分享的小产品；
- 一个已经启动但陷入停滞的项目；
- 对现有工具的具体不满。

平台应像一支默认替用户做事的虚拟产品团队。用户不需要理解完整领域模型、证据等级和工程对象，只需看到必要的选择、当前成果和诚实的限制。

### 3.2 企业用户

企业用户可能带来：

- 战略目标和客户问题；
- 已有产品、代码库、数据和流程；
- 品牌、预算、法规和组织权限；
- 多个利益相关方的冲突需求；
- 供应商、实验室和外部工程工具。

平台应提供一支可治理、可审计、可接入现有系统的 AI 产品与工程团队，而不是绕过企业责任链。

### 3.3 不建立两个产品内核

个人版与企业版共享同一个“意图—产品—证据”模型，差别主要是交互复杂度和治理能力：

| 维度 | 个人用户 | 企业用户 |
|---|---|---|
| 初始输入 | 愿望、困扰、创意 | 战略目标、客户问题、已有系统 |
| 默认体验 | 托管式、低认知负担 | 可配置、跨角色协作 |
| 人工介入 | 少量关键取舍 | 权限、预算、合规、品牌和发布审批 |
| 数据边界 | 本地优先或个人云空间 | 租户隔离、组织策略、审计与保留策略 |
| 交付 | 可使用或可部署的产品 | 可集成、可运营、可审计的产品系统 |

## 4. 用户怎样与平台交互

### 4.1 交互原则

用户不应被要求先写出完整 PRD，也不应通过不断改 prompt 来承担产品迭代。

推荐交互循环：

```text
表达不完整想法
  → 平台展示“我目前怎样理解”
  → 用户纠正关键误解
  → 平台形成 Product Contract
  → AI 自主研究、生成、评审、测试和修复
  → 用户直接使用阶段性成果
  → 平台收集结果反馈并继续推进
  → 达到交付门槛或明确说明尚缺什么
```

平台提问必须满足至少一个条件：

- 答案会显著改变产品目标或方案空间；
- 涉及价值冲突，AI 无权替用户决定；
- 涉及隐私、安全、预算或不可逆操作；
- 平台无法从已有资料、工具或低成本试验中获得答案。

能够通过研究、原型和测试自行回答的问题，不应转化成用户问卷。

### 4.2 三种协作模式

#### 托管模式

面向个人和非专业用户。AI 默认主动推进，只在关键节点请求输入。研究细节、工程对象和证据图默认折叠，但可以展开。

#### 共同设计模式

面向产品经理、设计师、工程师和创业团队。用户可以查看并修改问题模型、产品论点、候选分支、实验计划和版本差异。

#### 治理模式

面向企业和高风险项目。增加角色权限、组织政策、预算、数据边界、具名审批、法规和发布 Gate。

三种模式改变呈现与权限，不改变底层事实和证据语义。

### 4.3 Product Studio 的五个最小工作区

#### A. 对话与指挥

用于：

- 表达目标和补充情境；
- 纠正事实与解释；
- 询问为什么选择某条路径；
- 要求继续、暂停、回退、分叉或扩大探索；
- 发起工具和现实验证请求。

对话消息不是最终项目状态。被接受的内容必须投影为结构化、版本化对象。

#### B. 产品契约

以简洁、可纠正的形式持续展示：

- 为谁改变什么结果；
- 在什么情境下成立；
- 用户真正重视和拒绝的是什么；
- 成功、失败和停止条件；
- 时间、经济、隐私、安全和维护限制；
- 当前哪些内容是事实、假设或未知。

“Product Contract”是面向用户的综合投影；底层可以由 `ProductIntent`、`ProblemModel`、`OutcomeContract` 和当前交付状态共同组成，不要求用户理解这些内部对象。

#### C. 产品工作台

直接展示和运行 AI 产生的成果：

- 可运行的软件预览；
- 界面、交互流程和内容；
- 代码、测试和构建结果；
- 硬件概念、结构、仿真和样机材料；
- 服务蓝图、运营流程和现场执行材料；
- 不同 revision 的可感知差异。

平台应优先让用户使用成果，而不是阅读成果描述。

#### D. 决策与待办

只呈现需要人参与的事项。每项至少说明：

- 为什么需要人决定；
- 不同选择会改变什么；
- AI 的建议及其依据；
- 最晚决定时间和不决定的后果；
- 是否可以委托给平台继续探索。

#### E. 证据与进度

展示：

- 已验证、部分支持、被反驳和仍未知的声明；
- 已执行的测试和失败历史；
- 当前版本能够被称为什么；
- 尚不能声称什么；
- 下一步最值得消除的不确定性；
- 当前时间、成本和资源消耗。

进度不能只用百分比表示。对于探索性研发，更真实的进度是关键未知是否被消除、产品是否越来越接近可交付结果。

## 5. 端到端产品生成流程

### 5.1 意图协商

输入可能只有一句话、一次抱怨、已有项目资料、一个代码仓库或一组业务指标。

平台需要识别：

- 用户希望什么发生改变；
- 谁受到影响，谁拥有决定权；
- 用户明确拒绝什么结果；
- 哪些约束确定，哪些只是当前假设；
- 用户愿意投入多少时间、成本和注意力；
- 这是创建新产品、改造现有产品还是改变流程的问题。

输出不是立即生成的产品，而是一个可纠正的 `ProductIntent`。

### 5.2 问题与现实建模

平台主动形成并比较多个解释，而不是过早锁定一个需求：

- 用户、任务、环境和社会关系；
- 当前行为链和失败点；
- 已有替代方案及其不足；
- 心理、人因、物理、经济、技术和组织约束；
- 利益相关方之间的目标冲突；
- 可以低成本验证的竞争性问题解释。

输出是版本化的 `ProblemModel`，其中事实、推断、未知和竞争解释必须分开。

### 5.3 结果契约

在大规模生成前形成 `OutcomeContract`：

- 目标人群和适用条件；
- 希望改变的行为、体验或业务结果；
- 可观察成功指标；
- 最低可接受交付水平；
- 禁止结果和风险边界；
- 时间、成本、维护和数据限制；
- 现实验证需求；
- 失败、停止和重新定义问题的条件。

Outcome Contract 不是一次冻结后永不改变的 PRD。变化必须创建 revision，并明确哪些下游对象需要重新评估。

### 5.4 产品论点搜索

平台生成的是多个 `ProductThesis`，而不只是同一界面的换皮。每个论点需要说明：

- 它如何改变目标结果；
- 依赖哪些机制和条件；
- 为什么比现有替代方案更可能有效；
- 需要软件、硬件、服务、内容还是流程改变；
- 最大的不确定性是什么；
- 最便宜、最快的证伪方法是什么；
- 成功后的交付与维护成本是什么。

产品论点可以被并列、组合、暂停或淘汰，不强制得出一个综合分最高的“赢家”。

### 5.5 实现与内部迭代

选定探索分支后，AI 承担大部分循环：

```text
生成
  → 确定性规则检查
  → 独立评审
  → 构建与工具执行
  → 自动测试
  → 失败定位
  → 修复
  → 回归测试
```

用户第一次看到的正式候选不应是模型的第一次输出，而应是已经经过若干轮内部评审、测试和修复的结果。

### 5.6 现实验证

平台按声明风险选择验证方法：

- 代码和交互可以通过构建、单元测试、浏览器测试和可访问性检查；
- 用户是否理解、愿意使用以及行为是否改变，需要任务测试、研究或运行数据；
- 物理性能需要 CAD/CAE、样机、测量和实验室结果；
- 制造、成本、法规和供应能力需要真实外部数据和具名责任人；
- 商业结果需要在真实运营条件下观察。

AI 可以设计实验、操作工具、整理数据和提出解释，但不能把内部自评升级为现实结果证据。

### 5.7 交付与持续演化

每次正式交付至少包含：

1. 产品主体：可运行、可制造或可执行的成果；
2. 有效 revision 和构建/资产版本；
3. 已通过的验收项目；
4. 未验证或仅部分支持的声明；
5. 适用与不适用条件；
6. 剩余风险、维护要求和后续建议；
7. 必要的部署、导出、回滚和数据迁移能力。

产品上线后的行为、事故、纠正和结果继续进入产品模型，但不应不经审批自动改变高风险规则或推断敏感人格/健康信息。

## 6. 心理学与其他知识的正确位置

### 6.1 心理学是约束与机制层，不是总分层

心理学的作用是帮助平台理解人与产品互动时可能发生什么，并压缩明显无效或有害的方案空间。它不应被用于：

- 从有限行为推断人格、健康或稳定偏好；
- 给产品生成一个跨情境的心理学总分；
- 用一个研究结论替代目标用户和现实情境；
- 把相关性包装成普遍因果规律；
- 自动决定什么是用户应该追求的生活。

一条心理知识进入产品决策时，推荐的转换链是：

```text
观察到的行为或困难
  → 可能涉及的心理构念
  → 带条件的机制假设
  → 可以调整的产品变量
  → 预期的行为或体验变化
  → 可观察指标
  → 反例、失效条件和验证方法
```

### 6.2 区分三类人的知识

1. **相对稳定的人类能力与限制**：知觉、注意、记忆、动作、学习和决策等；
2. **特定人群与情境研究**：只能在明确适用条件内使用；
3. **具体个人的行为与偏好**：需要同意、持续纠正和最小必要保留，不能由一次行为自动泛化。

### 6.3 多类规律共同限制产品空间

- 数学、物理和工程规律约束“能否成立”；
- 心理学、人因和行为科学约束“人能否理解、愿意使用、使用时会发生什么”；
- 经济、组织、文化、审美和法规约束“能否被接受并持续存在”；
- 真实运行和实验决定某个产品在指定条件下是否真的产生目标结果。

这些规律能够排除错误和缩小搜索空间，但不能从理论上推出唯一最佳产品。平台应寻找满足硬约束后的多目标/Pareto 候选，并保留情境化权衡。

## 7. AI 与人的职责边界

### 7.1 AI 默认承担的工作

- 从不完整表达中提取目标、矛盾、未知和隐含约束；
- 读取用户授权的文档、代码、数据和现有产品；
- 研究现有行为、竞品、替代方案和相关证据；
- 形成多个竞争性问题解释；
- 生成有真实差异的产品论点；
- 制作软件、界面、内容、测试、工程材料和交付文档；
- 编排浏览器、代码、CAD、CAE、DFM、数据分析和测试工具；
- 在预算内执行多轮生成、评审、失败定位、修复和回归；
- 维护 revision、dependency、provenance、成本和审计记录；
- 主动暴露不确定性、风险、替代解释和所需现实资源；
- 当结果不支持原方向时，建议回退到问题模型或产品论点层。

### 7.2 必须由人承担或授权的工作

- 决定什么值得追求以及哪些伤害不可接受；
- 提供 AI 无法获得的隐性组织、文化和现实情境；
- 授权访问敏感数据、外部系统、资金和现实设备；
- 决定真正的价值冲突和不可逆选择；
- 对法规、安全、制造、质量和发布结论承担具名责任；
- 参与或组织无法被仿真替代的真实使用验证；
- 决定是否接受剩余风险和维护责任。

### 7.3 人工参与的目标

人工参与不是越少越好，也不是越多越可信。目标是 **最小必要、高信息量、责任清晰**。

平台必须避免两种失败：

- 把本应由 AI 调研或测试的问题反复问给用户；
- 为了“自动化”而替用户做价值判断或批准现实风险。

---

## 8. 防止高成本地产生垃圾

### 8.1 迭代成本应主要由平台承担

迭代不会消失，但大部分迭代应发生在平台内部。平台不应把低质量初稿、互相矛盾的 Agent 输出和未经运行的代码都展示给用户，让用户充当免费的集成测试人员。

### 8.2 先定义结果，再扩大生成

`OutcomeContract` 至少约束：

- 目标变化；
- 可观察成功标准；
- 交付级别；
- 用户可承受的时间、经济和维护成本；
- 禁止结果；
- 必须获得的现实证据。

没有这一层时，大量候选生成只会更快地产生无关成果。

### 8.3 交付成熟度必须显式

建议使用以下成熟度语义，具体枚举在实现 ADR 中确定：

| 层级 | 可以声称 | 不能声称 |
|---|---|---|
| Concept | 产品论点和待验证机制已表达 | 有效或可交付 |
| Runnable Prototype | 可以运行或体验，基础检查已通过 | 真实用户结果、生产可靠性 |
| Field Trial | 已在限定真实条件下试用并取得结果 | 跨情境普遍有效 |
| Operational Candidate | 部署、监控、回滚和关键验收已具备 | 未完成的法规/制造/市场结论 |
| Released Product | 指定范围和 revision 获得正式发布批准 | 超出批准范围的承诺 |

### 8.4 禁止伪完成

以下情况不能被标记为“产品已完成”：

- 只生成 PRD、分析报告或静态效果图；
- 代码没有成功构建和运行；
- 自动测试不存在或关键失败被忽略；
- 关键目标结果没有任何可观察验证路径；
- 仿真结果被当作物理、行为或商业结果；
- 用户仍需自行整合大量互不兼容的输出；
- 已知高风险未知被隐藏在乐观摘要中。

## 9. 建议的上位领域模型

以下对象是后续建模方向，不代表已经实现，也不应在没有 ADR 和 vertical slice 的情况下立即全部编码。

```text
ProductIntent
  ↓
ProblemModel
  ├─ ObservedFact
  ├─ Assumption
  ├─ Unknown
  ├─ CompetingExplanation
  └─ StakeholderTension
        ↓
OutcomeContract
  ├─ TargetOutcome
  ├─ SuccessIndicator
  ├─ ProhibitedOutcome
  ├─ ResourceBoundary
  └─ StopCondition
        ↓
ProductThesis[]
  ├─ MechanismHypothesis
  ├─ RealizationMode
  ├─ FalsifiablePrediction
  └─ ValidationStrategy
        ↓
ProductProgram / RealizationPlan
  ├─ DesignBrief(s)
  ├─ DesignCandidate(s)
  ├─ ProductArtifact(s)
  ├─ EngineeringObject(s)
  └─ DecisionRequest(s)
        ↓
Evaluation / Evidence / Release
```

### 9.1 与现有对象的关系

| 新上位概念 | 与当前系统的关系 |
|---|---|
| `ProductIntent` | 新增；允许保存不完整意图、价值和明确拒绝项 |
| `ProblemModel` | 新增；吸收 teardown/discovery、研究和用户纠正，但不等同于其中任何一个 |
| `OutcomeContract` | 新增；位于 `DesignBrief` 之前，定义目标结果和交付边界 |
| `ProductThesis` | 新增；表示竞争性产品路径，不等于视觉/交互候选 |
| `DesignBrief` | 保留；成为某一产品论点下的实现简报，而不是全平台入口 |
| `Evidence` / `Observation` / `ExperienceHypothesis` | 保留；成为问题模型和验证层的可信对象 |
| `DesignCandidate` / `VariablePatch` | 保留；用于具体 realization branch 的设计搜索和迭代 |
| Engineering / Quality objects | 保留；用于物理产品和高要求系统的工程验证与发布 |
| `TeardownResult` / `DigitalExperienceDiscovery` | 保留；成为问题建模的一种输入来源 |

### 9.2 活的产品模型

平台长期价值不只是保存聊天历史，而是维护一个随现实证据变化的“活的产品模型”：

- 当前目标结果；
- 用户和情境边界；
- 问题解释与竞争假设；
- 产品承诺和验收标准；
- 设计、代码、工程与运行资产；
- 每项关键声明的证据；
- 未解决的不确定性；
- 决策、责任人和适用 revision；
- 上线后的真实结果和问题。

## 10. 面向用户的产品形态决策

### 10.1 主产品：Web Product Studio

主界面采用 Web 工作空间，原因是它需要同时承载：

- 对话；
- 结构化契约和问题模型；
- 运行中的产品预览；
- 版本差异；
- 证据、任务、决策和审批；
- 图片、视频、代码、工程资产和图关系。

聊天产品无法稳定承载这些长期状态；纯桌面原生界面会过早增加多端成本；CLI 对普通用户认知负担过高。

### 10.2 CLI 的定位

CLI 继续负责：

- 批处理和可复现执行；
- CI、评测和回归；
- 数据导入导出与迁移；
- 管理和故障恢复；
- 高级用户自动化。

CLI 不再作为普通用户完成整个产品项目的推荐入口。

### 10.3 MCP 的定位

MCP 继续负责：

- 从 IDE、Codex、Claude 等外部环境读取项目状态；
- 发起受权限控制的草稿、查询和任务；
- 将 psyteardown 的产品模型提供给其他 AI 工具。

MCP 不是平台的唯一 UI，也不能绕过 Domain Command、权限、预算和 Gate。

### 10.4 可选桌面封装

当本地文件、隐私、离线运行和桌面集成需求被验证后，可以用 Tauri 包装同一 Web 前端和本地 API。首版不维护独立桌面产品，不优先采用 Electron。

## 11. 技术架构决策

### 11.1 当前阶段采用

#### 前端

- React；
- TypeScript；
- Vite；
- 基于 API schema 生成或校验客户端类型；
- 使用 query/cache 层管理服务端状态；
- 对话、工作台、决策和证据视图共享统一项目 revision 上下文。

选择 SPA 而不是 Next.js 的原因：当前产品是高度状态化的工作台，不依赖 SEO；业务和领域逻辑继续位于 Python 应用层，可以避免形成第二套服务端规则。

#### 后端

- FastAPI 提供 `/api/v1`；
- Pydantic 保持领域边界与 DTO 校验；
- 写操作使用显式 Domain Command 和 `expected_revision`；
- 读操作可以提供面向页面的组合 projection，但 projection 不承载写逻辑；
- 耗时操作返回 `job_id`，不绑定 HTTP 请求生命周期。

这一选择延续既有本地 Review Workspace 和领域命令 API 的实现经验，但把工作台定位从“Review Workspace”扩展为完整 Product Studio。旧 ADR 只作为本地历史资料，不再作为公开产品方向文档。

#### 数据与资产

- 本地第一阶段继续使用 SQLite；
- 大文件、生成资产和工具原始结果进入内容寻址资产存储；
- 领域对象和资产只通过稳定 `asset_id` 关联，不暴露任意文件路径；
- 向量索引只用于辅助检索，不作为意图、决策、revision 和证据的主存储。

#### 长任务

- 第一阶段复用并增强现有持久化 Job + 单 Worker；
- 通过 Server-Sent Events 推送状态、日志摘要和待人决策；
- 每一步保存输入 revision、输出、费用、模型/工具版本和检查点；
- 工作流必须支持暂停、恢复、取消、预算耗尽和 stale input 处理。

#### 隔离执行

当平台生成和执行真实代码时，增加容器化沙箱：

- 独立 workspace；
- CPU、内存、时间和磁盘限制；
- 默认受限网络；
- Secret 不写入生成内容和日志；
- 依赖安装与外部调用可审计；
- 构建产物和测试日志内容寻址保存。

Web 产品验证优先接入 Playwright，至少覆盖启动、关键任务、错误状态、可访问性基础检查和视觉回归。

### 11.2 后续托管/企业阶段

当多人并发、云端运行和企业接入被真实需求触发后，再演进为：

```text
React/TypeScript
FastAPI
PostgreSQL
S3-compatible object storage
durable workflow runtime（优先评估 Temporal）
隔离执行节点
OIDC / RBAC / tenant isolation
OpenTelemetry / cost and audit observability
```

如果需要语义检索，可以使用 PostgreSQL `pgvector` 或独立索引，但结构化事实和 revision 仍以关系模型为权威来源。

### 11.3 当前不引入

在第一条用户闭环完成前，不默认引入：

- Kubernetes；
- Kafka；
- 多种消息队列并存；
- 为编排而编排的大量自治 Agent；
- 把 LangChain 或任一模型框架变成领域核心；
- 独立 Electron 客户端；
- 与 Python 内核重复的 Next.js 服务端业务逻辑；
- 仅为了“AI 原生”而替换稳定的关系数据库和显式状态机。

## 12. 模型、工具与工作流原则

### 12.1 模型不是系统状态拥有者

- 模型输出默认是 proposal；
- 应用服务决定 proposal 是否成为结构化对象；
- 领域状态由命令、策略和 revision 转换；
- 不把完整聊天上下文当作唯一记忆；
- 不能依赖某个模型“记得之前发生过什么”。

### 12.2 多模型可以存在，但不以投票制造真相

不同模型可以分别承担研究、生成、批评、代码、视觉和总结任务。需要保留独立运行与分歧，而不是简单多数投票。现实事实由来源、工具结果和验证决定。

### 12.3 工具结果与 AI 解释分离

- 原始工具调用和结果不可变保存；
- AI 解释引用具体结果 revision；
- 解释错误不修改原始结果；
- 上游输入改变时，相关解释、比较和发布状态按依赖关系过期。

### 12.4 成本和时间是一等约束

每个 Product Program 应有：

- 模型预算；
- 工具和基础设施预算；
- 用户时间预算；
- 最大并行探索数；
- 停止和升级条件；
- 低价值循环检测。

平台不能通过无限生成掩盖方向不清或验证缺失。

## 13. 第一条完整纵向切片

第一条新方向 vertical slice 应选择数字产品，而不是同时覆盖软件、硬件和企业协作。

目标流程：

```text
用户输入一个模糊目标
  → AI 形成 ProductIntent 和可纠正理解
  → AI 研究并生成 ProblemModel
  → 用户确认 OutcomeContract 的关键价值边界
  → AI 生成 2–3 个有真实差异的 ProductThesis
  → 人选择或授权 AI 先做低成本证伪
  → AI 构建一个可运行 Web 产品
  → 构建、Playwright 和确定性检查失败后自动修复
  → 用户在 Product Studio 中直接使用
  → 反馈锚定到页面、任务和 revision
  → AI 迭代并形成可导出/部署的交付包
```

### 13.1 该切片的最小交付

- 一个 Product Studio Web 壳；
- `ProductIntent`、`ProblemModel`、`OutcomeContract`、`ProductThesis` 的最小模型和 revision；
- 对话到结构化对象的 proposal/confirm 流程；
- 一个持久化、可恢复的生成 Job；
- 一个隔离的 Web 产品生成与运行环境；
- Playwright 关键任务测试；
- 产品预览、版本差异和用户反馈锚点；
- 可下载的源代码、构建物和交付说明；
- 明确展示已验证、未知和不应声称的内容。

### 13.2 首切片暂不包含

- 完整多租户和企业权限；
- 手机原生应用生成；
- 通用硬件制造闭环；
- 任意语言/框架的代码生成；
- 无限制自治和无人批准部署；
- 自动证明心理或商业结果；
- 复杂插件市场。

---

## 14. 实施阶段建议

### Phase A：上位模型和产品壳

- 确认本规格；
- 为四个上位对象分别写最小 ADR 和状态转换；
- 建立 FastAPI API 壳和 React/Vite Product Studio；
- 将现有 Coordinator 暴露为应用服务，而不是复制业务逻辑；
- 建立项目主页、对话、产品契约、工作台、决策和证据五区的信息架构。

### Phase B：数字产品闭环

- 模糊意图到 Outcome Contract；
- 多 Product Thesis；
- 生成可运行 Web 产品；
- 沙箱构建、Playwright 测试和自动修复；
- 产品预览、反馈与版本迭代；
- 源码/构建物/证据包导出。

### Phase C：真实结果验证

- 可操作 Outcome Measure；
- 小规模真实任务试用；
- 运行事件、用户报告和测量的来源边界；
- Outcome Evidence Review；
- 从结果回退到 Product Thesis 或 ProblemModel 的闭环。

### Phase D：个人交付与企业治理

- 个人本地/托管体验；
- 身份、组织、权限和租户隔离；
- 预算、数据策略、审批和审计；
- Git、工单、数据仓库和部署平台集成；
- 多人评论、通知和冲突处理。

### Phase E：Realization Packs

在数字产品路径被验证后，再逐步增加：

- 移动应用；
- 硬件与工业设计；
- 服务设计和运营；
- 内容与教育产品；
- 企业内部流程和工具。

每个 pack 复用 Product Intent、Outcome Contract、Evidence 和 revision 内核，但拥有自己的生成器、工具、验证方法和发布 Gate。

Transit Anchor 继续作为硬件 realization pack 的验证案例，而不是整个平台的唯一北极星。

## 15. 衡量平台是否真的有价值

### 15.1 用户价值指标

- 从模糊输入到首个可纠正 Product Contract 的时间；
- 从意图到首个可运行成果的时间；
- 首次正式交付可接受率；
- 用户为获得可用结果需要回答的问题数和总耗时；
- 用户需要亲自发现的基础构建/交互错误数；
- 产品在目标任务上的真实改善；
- 达到相同结果所需的时间和经济成本；
- 交付后仍需用户自行整合和返工的比例。

### 15.2 AI 工作质量指标

- 平台内部完成并成功收敛的迭代数；
- 无来源事实和过强声明比例；
- 自动测试首次失败后修复成功率；
- 关键未知识别和消除率；
- 错误方向在低成本阶段被证伪的比例；
- 上游变化后受影响对象的正确失效传播率；
- 预算内完成率和低价值循环率。

### 15.3 不使用的虚荣指标

- 报告字数；
- Agent 数量；
- 生成候选总数；
- 模型调用次数；
- 没有完成定义的“任务完成百分比”；
- 未与用户结果关联的单一心理学或体验总分。

---

## 16. 与当前开发计划的关系

### 16.1 保留为可信研发内核

仓库现有代码与自动化测试继续作为以下可信研发内核能力的事实基线；旧实施计划仅在本地保留，不再作为公开产品文档：

- Discovery 和体验研究；
- 证据、观察和假设；
- DesignBrief、候选和 VariablePatch；
- 工程对象、依赖图和失效传播；
- 样机、测量、质量、法规和发布 Gate；
- 当前 CLI、MCP 和 SQLite 能力。

### 16.2 被本规格更新的定位

- 原文中的平台最终目标现在被视为“可信研发内核目标”，不再是完整用户产品北极星；
- App/数字服务拆解从默认入口变为 ProblemModel 的一种信息来源；
- `DesignBrief` 从起点变为 Product Thesis 下的 realization 对象；
- CLI/MCP 从主要使用方式变为辅助接入方式；
- Transit Anchor 从平台主线变为硬件 realization pack 的试点；
- Discovery/CLI 收敛仍可作为维护任务，但不应替代第一条 Product Studio 用户闭环。

### 16.3 当前事实边界不变

本次方向升级不会提高任何现有案例的证据等级。Transit Anchor 仍然没有实体样机、MeasurementObservation 或 EvidenceReview，不能声称舒适、安全、可靠、可制造或可发布。

---

## 17. 后续需要单独决策的问题

以下问题不在本规格中提前锁死：

1. 第一条 vertical slice 的具体目标问题和目标用户；
2. `ProductIntent`、`ProblemModel`、`OutcomeContract` 和 `ProductThesis` 的最小字段；
3. Product Contract 中哪些字段必须由人确认，哪些可以由证据自动推进；
4. 第一版允许生成的 Web 技术模板范围；
5. 代码沙箱的本地实现和安全边界；
6. 模型/工具预算与失败恢复策略；
7. 产品预览如何采集用户反馈，同时避免未经同意的行为监控；
8. 何时从 SQLite/单 Worker 迁移到 PostgreSQL/Temporal；
9. 个人本地版、托管版和企业部署的优先顺序；
10. 平台名称是否继续使用 psyteardown，或把它作为可信分析内核名称。

这些问题应通过 ADR、原型和第一条真实用户闭环逐步回答，而不是在平台尚未产生可用产品前一次性设计完毕。

## 18. 最终判断

psyteardown 已经拥有一套谨慎、可追溯的体验与工程验证内核，但用户真正需要的不是更多分析对象、工作流或 Agent，而是让一件原本模糊而困难的事被推进成一个真实可用的结果。

下一阶段最重要的转变是：

```text
从“帮助专业人员分析和审查一个已经定义的产品”
转向“帮助用户定义、生成、验证并交付他们真正需要的产品”
```

平台必须同时坚持两件事：

1. AI 应承担绝大多数可自动完成的认知劳动、制作劳动和内部迭代；
2. 平台不能用流畅生成、模拟结果或乐观摘要伪装真实世界中的未知。

只有当用户能以较低认知和经济成本获得一个可运行、可验证、边界诚实且确实推进其目标的产品时，这个平台才实现了它真正的价值。
